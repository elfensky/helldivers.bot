<objective>
Replace the OG route's generated crash fallback with a committed static PNG served as raw bytes, and make cache behaviour depend on the render outcome so a single failure can no longer freeze the social card.

Vertical slice: after this plan a crawler that hits `/opengraph-image` during a render failure gets a real branded image, and the very next crawler gets a retry of the live card — neither of which happens today.

Purpose: STAB-02 (#503). The 2026-08-07 comment on #503 reframes the bug: it is not a 500, it is a *frozen fallback*. `revalidate = 300` caches whatever the route returned, and the current fallback is itself an `ImageResponse` that goes through Satori and sharp, so it can fail the same way the real card did.
Output: A committed 1200x630 fallback PNG plus its generator script, a rewritten fallback branch that touches no image pipeline, per-outcome cache headers, and unit coverage for both.
</objective>

    - Test 1: rasterisation succeeds -> exactly one `ImageResponse` is constructed, the response body is the rendered bytes, and no error is reported. (Existing case, must keep passing.)
    - Test 2: rasterisation rejects -> exactly one `ImageResponse` is constructed (the failed real card; the fallback constructs none), the returned response's `content-type` is `image/png`, and its `Cache-Control` header contains `no-store`.
    - Test 3: rasterisation rejects -> the underlying satori/sharp error is reported to GlitchTip with the route tag preserved.
    - Test 4: `getCampaign()` rejects -> the static fallback is served with `no-store`, and no `ImageResponse` is constructed at all.
    - Test 5: `getCampaign()` resolves with an empty `status` array -> same as Test 4.
    - Test 6: rasterisation succeeds -> the success response carries a `Cache-Control` header with a non-zero `max-age` or `s-maxage`, so the dynamic card is still cached.
  </behavior>
  <action>
    Rewrite the fallback so nothing in it can fail the way the real card does, and make caching depend on the outcome.

    **Replace `fallbackImage()`.** It currently returns an `ImageResponse`, which per D-07 goes through Satori and sharp and can fail identically. Make it an async function that reads `public/og-fallback.png` through `fs/promises` `readFile`, resolving the path against `process.cwd()` (in the standalone runtime image `public/` sits next to `server.js`, and `process.cwd()` is that directory — confirmed in `Dockerfile.app`). Wrap the read in `tryCatch`, and return the buffer in a `Response` with `content-type: image/png` and a `Cache-Control` value of `no-store`. If even the file read fails, report it through `reportError` and return a 1x1 transparent PNG built from an inlined base64 constant so the route still cannot 500 — that constant is the only place a byte literal belongs.

    **Split the cache decision.** `export const revalidate = 300` is segment-level: it caches whatever the route returned, which is exactly how a single failure froze the card. Per D-08 the fallback must never be cached while the real card still should be. Segment-level ISR cannot distinguish the two outcomes, so move the decision into the response: remove the `revalidate` export, add `export const dynamic = 'force-dynamic'` so the framework stops caching the segment, and set the cache policy explicitly on each returned `Response`. The success response gets a public policy with a 300-second shared max-age and a short stale-while-revalidate window, preserving the current 5-minute freshness. The fallback response gets `no-store`. Note this is a decision recorded in D-08 as reversible: the semantics are route-local.

    **Keep `renderOrFallback()`'s shape.** It already awaits `arrayBuffer()` inside `tryCatch` to pull the rasterisation forward where it is catchable — do not change that. Change only what it returns on each branch: the error branch awaits the new static fallback, and the success branch builds its `Response` with the success cache headers rather than passing the `ImageResponse`'s own headers through unchanged.

    **Route error reporting through `reportError`.** The file currently calls `Sentry.captureException` directly with a `route: 'opengraph-image'` tag. Move that to `reportError` from `@/shared/utils/observability.mjs` for consistency with the rest of the codebase, preserving the route tag and adding a `stage` distinguishing a rasterisation failure from a data-fetch failure. Do not double-report: one call per failure.

    Then extend the unit suite to cover all six behaviours. The existing `next/og` mock with its `bodyFails` flag and the `getCampaign` mock are the scaffolding to extend, not rebuild. Mock `fs/promises` `readFile` so the tests do not depend on the committed binary. Write the new cases before the source change and confirm they are red for the right reason.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Unauthenticated crawler -> `/opengraph-image` | Any party (Discord, Slack, Google, an attacker) can request the route at any rate; the route reads the database and runs an image pipeline per uncached request |
| Postgres -> OG render | `getCampaign()` supplies the shape the Satori tree is built from; a shape the renderer cannot handle becomes a 500 |
| Runtime filesystem -> fallback response | The fallback branch reads a file from disk and returns its bytes to an unauthenticated caller |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Denial of Service | `/opengraph-image` uncached render path | high | mitigate | Removing segment `revalidate` in favour of `dynamic` plus explicit headers must not remove caching from the success path: Task 2 requires a non-zero shared max-age on every successful render, and Task 3 verifies it against a production build, so an unauthenticated crawler cannot force a Satori+sharp render per request |
| T-03-02 | Information Disclosure | Fallback file read | medium | mitigate | The read target is a hard-coded constant path joined to `process.cwd()`; no request-derived value reaches the path, so no traversal input exists. (Generic path-traversal is canon — covered by `/gsd-secure-phase` and eslint security rules; not minted as a bespoke prohibition.) |
| T-03-03 | Denial of Service | Cached poisoned fallback | high | mitigate | `no-store` on the fallback response plus the Task 3 recovery observation ensures one transient failure cannot pin a permanent degraded card in front of every consumer |
| T-03-04 | Information Disclosure | Error reporting on the render path | low | mitigate | Failures route through `reportError`, which sends to GlitchTip and returns an image to the caller; no stack, message or database detail reaches the response body |
| T-03-05 | Spoofing | Static fallback content | medium | mitigate | The plan's prohibition forbids game state on the fallback, so a degraded card can never present fabricated or stale war data as if it were live |
</threat_model>

## Flagged Assumptions (edge probe — spec-less fallback)

- **STAB-02 / unclassified — unresolved.** The edge probe returned "unclassified — review manually" for STAB-02. Recorded here rather than dropped. Reviewed manually during planning: the requirement carries two separable edge dimensions — the *failure* axis (which upstream failures reach the fallback: rasterisation reject, data-fetch reject, empty result set) and the *cache* axis (what happens on the request after a failure). Both are covered by Task 2's six behaviours and Task 3's five-request sequence. The third dimension named by STAB-02 — edge-case map states — is covered in plan 01-04, not here.
- **`process.cwd()` in the standalone image is asserted from `Dockerfile.app`, not observed.** `COPY --from=builder /app/public ./public` places `public/` beside `server.js`, and `node .next/standalone/server.js` is started from that directory, so `process.cwd()` resolves. Task 3's production-build run is what turns this from an assumption into evidence; if the fallback read fails there, the resolution strategy needs revisiting before release.
</flagged_assumptions>
