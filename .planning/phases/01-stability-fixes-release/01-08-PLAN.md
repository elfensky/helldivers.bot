    What remains is the release itself — a protected-branch operation with an irreversible step in the middle. `main` is PR-only, and the `vX.Y.Z` tag triggers the production Docker build. A tag pushed to the wrong commit, or a merge landed without a tag, both leave production in a state that cannot be undone by reverting a file.

    The exact sequence I will run after your approval, from CLAUDE.md § Git Workflow rule 3:
    1. `gh pr create --base main --head develop` and merge it — **merge commit only**, never squash, never rebase
    2. `git tag vX.Y.Z` on the resulting merge commit on `main`, and push the tag
    3. Wait for the production Docker build the tag triggers, and confirm it succeeded
    4. `git checkout develop && git merge origin/main && git push` — the merge-back that carries main's PR merge commit into develop so the next release PR does not trip the "branch not up to date" check
    5. Record the released version, the tag, the merge commit sha and the derived deployment id in `01-RELEASE-RECORD.md`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local git -> protected `main` branch | `main` is PR-only; the release crosses from unprotected working history into the branch production builds from |
| Version tag -> production deployment | Pushing a tag is the trigger that ships an image to real users; nothing else gates it |
| Repository secrets -> release build | `SENTRY_PROJECT` and the sourcemap upload credentials are consumed by the tag-triggered workflow |
| Sourcemaps -> GlitchTip host | The release uploads original source structure to a self-hosted service |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-01 | Elevation of Privilege | Direct push to `main` | high | mitigate | The release goes through `gh pr create --base main`; the plan never writes to `main` directly, and the branch protection that makes it PR-only is the enforcing control |
| T-08-02 | Tampering | Tag pointing at the wrong commit | high | mitigate | The verify step asserts the semver tag points at the current tip of `origin/main` and matches `package.json`'s version, so a tag on a stale or unrelated commit fails the gate rather than shipping |
| T-08-03 | Information Disclosure | Sourcemaps uploaded to GlitchTip | medium | accept | PROJECT.md records the standing decision that sourcemaps leave the image only once symbolication is proven (#502, scoped to Phase 2). For this release they are uploaded to a self-hosted GlitchTip the developer controls, which is the accepted trade-off that makes the 48h window readable |
| T-08-04 | Information Disclosure | Secret values in the release record | high | mitigate | The plan records `gh secret list` output by name only; no secret value is written to any committed document |
| T-08-05 | Repudiation | Half-completed release | high | mitigate | Three separate assertions — tag on the remote, tag matching the version, `main` an ancestor of `develop` — turn each of the two silent half-completion modes (merged-without-tag, tagged-without-build) into a failed gate |
| T-08-06 | Denial of Service | Shipping a known-broken build | high | mitigate | Task 2 stops the plan on any failed pre-release check, including an ABSENT VAPID verdict that would put every push-capable visitor into the new error state |
</threat_model>
