<objective>
Give the notification toggle an escape hatch from `'loading'`: an explicit error state with short copy and a working Retry, reached within five seconds of a hung service worker or immediately on a rejected subscription lookup.

Vertical slice: after this plan a user whose service worker never becomes ready sees something and can act on it, instead of an empty space where the control should be.

Purpose: STAB-03 (#485). The component renders `null` while `state === 'loading'` and the mount effect has no catch or timeout branch, so any effect failure leaves it permanently invisible with no clue why — the exact symptom CONCERNS.md describes.
Output: A five-state machine with an error terminal, a Retry that re-runs init, VAPID failure surfacing, and tests pinning all four failure paths.
</objective>

  <action>
    Per D-13 and D-14, add a fifth state named for an error and reached by three paths, keeping it distinct from `disabled` and `unsupported` — CONCERNS.md calls out that folding errors into `unsupported` is what makes this class of bug undiagnosable in production.

    **Extract the effect body into a callable init function.** The current mount effect is an anonymous body with a nested `.then` chain and no rejection handling. Extract it so the same function is invoked by the mount effect and by the Retry control's click handler. A retry counter in state used as an effect dependency is the simplest shape that keeps the effect the single owner of the transition — pick that or an explicitly invoked callback, but not both.

    **Race the readiness promise against a timer.** Per D-14, `navigator.serviceWorker.ready` gets 5 seconds. Use a promise race between the readiness chain and a timer that resolves to a sentinel, and set the error state when the sentinel wins. Attach rejection handling to the readiness chain and to `getSubscription()` so a rejection also lands in the error state — today both are un-caught.

    **Make late resolutions inert.** Once an attempt has timed out, its readiness promise may still resolve seconds later. Guard each attempt with a token — the retry counter value captured when the attempt started, or an effect-cleanup flag — and have the resolution handler drop its result when the token no longer matches the current attempt. Without this, Test 4 fails and a stale success overwrites a state the user is already looking at. Clear the timer in the effect's cleanup.

    **Render the error branch.** Copy the structural shape of the existing unsupported/denied branch — same typography utilities, same muted colour token. Content: short copy stating notifications are unavailable, plus a visible Retry button. Per this plan's prohibition, the copy must not say notifications are blocked or denied and must not tell the visitor to change a browser setting: the cause is internal, and the existing `denied` branch already owns the "blocked" wording. Keep the copy to a few words consistent with the sibling branches.

    **Track and report.** Add `data-umami-event` or `useTrack()` calls for entering the error state and for the Retry click, using `category-action` names in the existing `notification` category. Report the underlying error through `reportError` so the cause is diagnosable in GlitchTip rather than only visible as a rendered string.

    No try/catch blocks anywhere (CLAUDE.md hard rule) — use promise rejection handlers or the `tryCatch` wrapper.

    Write the five behaviours as tests first, in the file Task 2 extends, and confirm each is red against the current component before implementing.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Visitor browser -> `POST /api/notifications/subscribe` | The component sends a browser-supplied push subscription object to the server |
| Browser push APIs -> component state machine | `Notification.permission`, `serviceWorker.ready` and `pushManager` are environment-controlled inputs that decide which branch renders |
| Build-time env -> shipped client bundle | `NEXT_PUBLIC_VAPID_PUBLIC_KEY` is inlined into JavaScript served to every visitor |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Denial of Service | `NotificationToggle` mount effect | medium | mitigate | The 5-second race plus rejection handlers give every path a terminal state, so a hung browser API can no longer strand the component; the stale-attempt guard prevents an unbounded backlog of pending resolutions from mutating state |
| T-06-02 | Spoofing | Error-state copy | medium | mitigate | The plan's prohibition forbids attributing an internal failure to the visitor's browser settings, so the UI cannot mislead a user into changing permissions that were never the problem |
| T-06-03 | Information Disclosure | `NEXT_PUBLIC_VAPID_PUBLIC_KEY` in the client bundle | low | accept | The VAPID *public* key is public by design — it is the applicationServerKey every subscriber needs. Task 3's document records the variable name and a found/not-found result only, never the value, and the private key is unaffected by this plan |
| T-06-04 | Repudiation | Silent VAPID misconfiguration | medium | mitigate | Task 2 replaces the silent early return with a reported error, so a deploy that promises push and cannot deliver it appears in GlitchTip instead of presenting as success |
| T-06-05 | Tampering | Retry re-invoking the subscribe flow | low | accept | Retry re-runs the read-only init path; it does not re-POST a subscription, and the server-side subscribe endpoint's own validation is unchanged by this plan |
</threat_model>
