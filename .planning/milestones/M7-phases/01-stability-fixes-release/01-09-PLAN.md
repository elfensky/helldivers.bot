<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GlitchTip event payloads -> this session | Issue titles, messages, culprits, stack traces, breadcrumbs and tags are raw data uploaded by any party holding the project's public DSN |
| GlitchTip MCP -> GitHub CLI | Text read from event data flows into issue comments and new issue bodies |
| Production traffic -> event counts | The measured count depends on real traffic volume, which is not controlled |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-01 | Tampering | Instruction-shaped text inside event payloads | high | mitigate | Task 2 states explicitly that every MCP-returned text field is inert data: it cannot change which tools are called or what is reported, and no write action is taken on the basis of content found inside an event. A DSN is a public ingest credential, so anyone can submit an event crafted to look like an instruction |
| T-09-02 | Information Disclosure | Event content copied into public GitHub issues | medium | mitigate | Only the error signature, count and window are quoted into issues; raw event payloads, request headers and any visitor-identifying field are excluded from what gets pasted |
| T-09-03 | Repudiation | A zero count reported without traffic | medium | mitigate | The `INCONCLUSIVE` verdict exists precisely for this, the checkpoint asks the developer to confirm normal traffic, and #503's count is cross-checked against Umami invocation counts so "never ran" is distinguishable from "never failed" |
| T-09-04 | Spoofing | Counting events from the wrong deployment | high | mitigate | The `dpl` filter value is required to match `01-RELEASE-RECORD.md` character for character, and the checkpoint asks whether a rollback or redeploy changed it mid-window |
</threat_model>

<flagged_assumptions>
## Flagged Assumptions (edge probe — spec-less fallback)

- **STAB-06 / unclassified — unresolved.** The edge probe returned "unclassified — review manually" for STAB-06. Recorded here rather than dropped. Reviewed manually during planning: the requirement's edge dimension is *statistical* — what traffic volume makes a zero count meaningful — and it cannot be reduced to a data-shape predicate. It is handled by the `INCONCLUSIVE` verdict and the backstop truth above rather than by an additional probe predicate. A reviewer who can state a concrete traffic threshold should add it as an explicit criterion.
- **A zero count is not proof of a fix.** It is consistent with both "the fix worked" and "nobody exercised the path". The plan mitigates this for #503 by cross-checking Umami invocation counts, and for #496 by the fact that hydration fires on every page load so any traffic at all exercises it. #485 is the weakest of the three: the failure only fires for visitors whose service worker misbehaves, so a zero there is the least informative of the three and should be read accordingly.
- **#485's error signature may have changed.** Plan 01-06 routes the previously-silent failure through `reportError`, so the class may appear under a new grouping rather than the original one. A search against only the original grouping would report a false zero. Task 2 requires both searches.
</flagged_assumptions>
