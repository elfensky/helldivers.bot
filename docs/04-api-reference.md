## 1. Response Envelope Formats

There are two distinct envelope formats in use. Which one is returned depends entirely on which route is handling the request.

### 1.1 Standard Envelope

Used by: `/api/healthcheck`, `/api/h1/campaign`, `/api/h1/update`.

Generated by `successResponse(code, start, data)` and `errorResponse(code, start, error)` in `src/utils/responses.mjs`.

**Success shape:**

```json
{
  "time": 42.5,
  "code": 200,
  "message": "OK",
  "data": { ... }
}
```

**Error shape:**

```json
{
  "time": 42.5,
  "code": 400,
  "message": "Bad Request",
  "error": "details or null"
}
```

The `time` field is the raw floating-point result of `performance.now() - start` (milliseconds elapsed since the handler began). It is **not** rounded — that is a separate utility (`roundedPerformanceTime`) used only for analytics payloads.

`message` is derived from a switch on the numeric `code`. The full mapping implemented in `responses.mjs`:

| code | message |
|------|---------|
| 200 | OK |
| 201 | Created |
| 202 | Accepted |
| 203 | Non-authoritative information |
| 204 | No content |
| 400 | Bad Request |
| 401 | Unauthorized |
| 403 | Forbidden |
| 404 | Not found |
| 405 | Method not allowed |
| 418 | I'm a teapot |
| 429 | Too many requests |
| 451 | Unavailable for legal reasons |
| 500 | Internal server error |
| 501 | Not implemented |
| 502 | Bad gateway |
| 503 | Service unavailable |
| other | Unknown error (HTTP status coerced to 500) |

`errorResponse` throws if called with a 1xx, 2xx, or 3xx code. `successResponse` throws if called with a non-2xx code.

### 1.2 Rebroadcast Envelope

Used by: `/api/h1/rebroadcast` error paths only.

```json
{
  "time": 1711234567,
  "error_code": 0,
  "error_message": "Invalid Content Type"
}
```

`time` is a Unix timestamp: `Math.floor(Date.now() / 1000)`. This intentionally mirrors the error format returned by the official Helldivers 1 API so that clients proxying to this service do not need to detect the source of an error response.

Successful rebroadcast responses bypass the envelope entirely — the raw JSON retrieved from the database is returned directly via `NextResponse.json(data)`.

## 2. GET /api/healthcheck

**Source:** `src/app/api/healthcheck/route.js`

**Auth:** None.

**Request:** No parameters.

**Response (200):**

```json
{
  "time": 0.123,
  "code": 200,
  "message": "OK",
  "data": { "alive": true }
}
```

**Method not allowed (405):** POST, PUT, DELETE, PATCH, OPTIONS — standard envelope.

**Notes:**

- The only logic in this handler is `successResponse(200, start, { alive: true })`. There is no database ping or dependency check; it indicates only that the Node.js process is alive and the route is reachable.
- Used as the Docker `HEALTHCHECK` target: `curl -f http://0.0.0.0:3000/api/healthcheck`.

## 3. GET /api/h1/campaign

**Source:** `src/app/api/h1/campaign/route.js`

**Auth:** None (public).

### Request

| Parameter | Location | Type | Required | Validation |
|-----------|----------|------|----------|------------|
| `season` | Query string | String coerced to integer | No | `isValidNumber`: must parse to a positive integer (`z.number().int().positive()`) |

### Behavior

```
1. If ?season present:
   a. Parse with isValidNumber.safeParse()
   b. On failure → 400 with Zod issue message
   c. On success → season = Number(param)

2. Query DB: getCampaign(season)
   - season = null → returns latest season with complete data
   - season = N → returns that specific season
   - On DB error → 500

3. If DB returned null (no local data):
   a. Call updateSeason(season)
      - On Zod validation failure with received === 'null':
        → 404 with "Couldn't find campaign with season N"
      - On other Zod error → 500 with issues array
      - On non-Zod error → 500 with error object
   b. Re-query DB: getCampaign(season)
      - On DB error → 500

4. Return successResponse(200, start, data)
```

The 404 branch is reached specifically when `updateSeason` receives a Zod parse error where `issues[0].code === 'invalid_type'` and `issues[0].received === 'null'`. This is the signal that the official API returned null for the requested season, meaning it does not exist.

### Response (200)

Standard envelope. `data` contains the season record with all relations loaded by `getCampaign`: campaigns, statistics, snapshots, defend events, attack events, introduction order, and points max.

```json
{
  "time": 38.2,
  "code": 200,
  "message": "OK",
  "data": { ... }
}
```

### Error Responses

| Code | Condition |
|------|-----------|
| 400 | `season` param present but not a positive integer |
| 404 | Season not found locally or remotely |
| 500 | DB error or unexpected fetch error |

### Analytics

Tracked via `after()` (Next.js deferred execution, runs after response is sent). Event name: `"API | Campaign"`, URL: `"/api/h1/campaign"`, custom property `ms` = `roundedPerformanceTime(start)` (elapsed rounded up to nearest 50ms). Only fires in production (`NODE_ENV === 'production'`).

### Method Not Allowed

POST, PUT, DELETE, PATCH, OPTIONS → 405, standard envelope.

## 4. POST /api/h1/rebroadcast

**Source:** `src/app/api/h1/rebroadcast/route.js`

**Auth:** None (public).

**Content-Type:** `multipart/form-data` or `application/x-www-form-urlencoded`. Any other value returns rebroadcast error code 0.

### Validation Pipeline

```
Step 1 — Content-Type
  isValidContentType.safeParse(contentType)
  Fail → rebroadcastErrorResponse(0) [HTTP 400]

Step 2 — action field presence
  formDataToObject(formData)
  typeof formValues.action !== 'string'
  Fail → rebroadcastErrorResponse(1) [HTTP 400]

Step 3 — Full FormData structure (Zod discriminated union)
  isValidFormData.safeParse(formValues)
  Fail with code 'invalid_union' → rebroadcastErrorResponse(2) [HTTP 400]
  Fail with code 'invalid_type'  → rebroadcastErrorResponse(3) [HTTP 400]
  Fail with other code           → rebroadcastErrorResponse(null) [HTTP 500]
```

### Actions

The Zod schema (`isValidFormData` in `src/validators/isValidFormData.js`) is a discriminated union on `action` with five branches. However, the route handler only processes two of them. The other three (`get_available_entitlements`, `get_leaderboards`, `get_usernames`) pass validation but fall through to the default case, resulting in `data = undefined` and rebroadcast error code 4 (Not found).

**Implemented actions:**

#### `get_campaign_status`

```
FormData: { action: "get_campaign_status" }
```

No extra parameters. Extra keys are rejected by the schema (`refine` asserts `Object.keys(obj).length === 1`).

Queries `rebroadcast_status` table via `queryGetRebroadcastStatus()`. Returns `row.data.json` directly.

This action is expected to always have data because `updateStatus()` runs on application startup (via the worker, which polls on startup). There is no remote-fetch fallback for this action.

#### `get_snapshots`

```
FormData: { action: "get_snapshots", season: "1" }
```

`season` is required and must be a positive integer (string coercion via `schemaNumber`). After validation, it is cast: `formValues.season = Number(formValues.season)`.

Queries `rebroadcast_snapshot` table via `queryGetRebroadcastSeason(season)`. If the result is `null` or `undefined`:

1. Calls `updateSeason(season)` to fetch from the official API and store.
2. On `seasonError`: returns rebroadcast error code 4.
3. On success: re-queries locally.

After the branch, if `data` is still `null` or `undefined`, returns rebroadcast error code 4.

### Successful Response

`NextResponse.json(data)` — raw JSON from the database. No envelope. HTTP 200.

### Rebroadcast Error Code Reference

| Code | HTTP Status | `error_message` | Condition |
|------|-------------|-----------------|-----------|
| 0 | 400 | Invalid Content Type | Content-Type is not form-data or urlencoded |
| 1 | 400 | No action set | `action` field missing or not a string |
| 2 | 400 | Invalid action | Zod `invalid_union` — action value not recognized |
| 3 | 400 | Missing or invalid arguments | Zod `invalid_type` — action recognized but params wrong |
| 4 | 404 | Not found | Data not in DB and remote fetch failed or returned nothing |
| 5 | 405 | Method not allowed | Non-POST method |
| null | 500 | Unknown error | Any other Zod error code |

All errors use the rebroadcast envelope: `{ time, error_code, error_message }`.

### Analytics

Tracked via `after()`. Event name: `"API | Rebroadcast"`. Note: the URL passed to `umamiTrackEvent` is hardcoded as `"/api/h1/update"` — this is a copy-paste bug in the source but does not affect runtime behavior. Custom properties include `action` (and `season` when action is `get_snapshots`) plus `ms`.

### Method Not Allowed

GET, PUT, DELETE, PATCH, OPTIONS → `rebroadcastErrorResponse(5)` [HTTP 405, rebroadcast envelope].

## 5. GET /api/h1/update (Internal)

**Source:** `src/app/api/h1/update/route.js`

**Auth:** `key` query parameter must exactly match `process.env.UPDATE_KEY`.

**Caller:** Worker thread (`public/workers/cron.js`) only. Not intended for external or user-facing consumption.

### Request

| Parameter | Location | Required | Validation |
|-----------|----------|----------|------------|
| `key` | Query string | Yes | Must equal `UPDATE_KEY` env var |

### Behavior

```
1. key param missing          → 400
2. key !== UPDATE_KEY         → 401
3. updateStatus()             → fetches and upserts current campaign status
   On error → 500 with statusError.message
4. updateSeason(statusData.season)  → fetches and upserts current season snapshot
   Uses season extracted from status response
   On error → 500 with seasonError.message
5. Return 200 with both results
```

Both steps use `tryCatch()`, which returns `{ data, error }` and never throws. Error messages are also logged to `console.error` before returning the 500 response.

### Response (200)

```json
{
  "time": 84.1,
  "code": 200,
  "message": "OK",
  "data": {
    "updated": {
      "status": { ... },
      "season": { ... }
    }
  }
}
```

`status` and `season` values are whatever `updateStatus()` and `updateSeason()` return, respectively.

### Error Responses

| Code | Condition |
|------|-----------|
| 400 | `key` query param absent |
| 401 | `key` present but does not match `UPDATE_KEY` |
| 500 | `updateStatus()` or `updateSeason()` threw |

For 400 and 401, `error` in the response body is `null` (default value — no third argument passed to `errorResponse`).

### Analytics

The `after()` hook exists in source but is entirely commented out. No analytics tracking occurs for this endpoint.

### Method Not Allowed

POST, PUT, DELETE, PATCH, OPTIONS → 405, standard envelope.

## 6. GET /api/og

**Source:** `src/app/api/og/route.js`

**Auth:** None.

**Request:** No parameters.

**Response:** PNG image, `1200 x 630` pixels, generated via `ImageResponse` from `next/og`.

The current implementation renders a white background with the text "Hello" at 40px. It is a placeholder for a dynamic Open Graph image used in social media link previews (`<meta property="og:image">`).

There are no error responses defined and no method-not-allowed handlers exported. Calling with a non-GET method will result in Next.js framework-level 405 behavior.

## 7. Auth Routes

**Path:** `/api/auth/[...nextauth]`

**Source:** `src/app/api/auth/[...nextauth]/route.js`

**Implementation:** The route file re-exports `{ GET, POST }` from the NextAuth.js v5 `handlers` object configured in `src/auth.js`.

**Providers:**
- Discord OAuth (`AUTH_DISCORD_ID`, `AUTH_DISCORD_SECRET`)
- GitHub OAuth (configured in `src/auth.js`; requires `AUTH_GITHUB_ID`, `AUTH_GITHUB_SECRET`)
- Nodemailer magic links (available in auth configuration but commented out in the active provider list)

**Session strategy:** Database-backed via Prisma adapter. Sessions are stored in the `Session` table, not in JWTs. This means session validity requires a database query on each request.

**Endpoints handled by NextAuth.js** (not exhaustive — framework-managed):

| Path | Method | Purpose |
|------|--------|---------|
| `/api/auth/signin` | GET | Sign-in page redirect |
| `/api/auth/signin/discord` | POST | Initiate Discord OAuth flow |
| `/api/auth/callback/discord` | GET | OAuth callback |
| `/api/auth/signout` | POST | Sign out |
| `/api/auth/session` | GET | Current session JSON |

## 8. Method Not Allowed Pattern

All routes except `/api/og` and auth export explicit handlers for unused HTTP methods. The pattern used throughout:

```js
const methodNotAllowed = () => {
    const start = performance.now();
    return errorResponse(405, start);
};

export const POST = methodNotAllowed;
export const PUT = methodNotAllowed;
export const DELETE = methodNotAllowed;
export const PATCH = methodNotAllowed;
export const OPTIONS = methodNotAllowed;
```

The rebroadcast route deviates: it uses `rebroadcastErrorResponse(5)` instead of the standard `errorResponse`, and its method-not-allowed handler does not call `performance.now()` (not needed since the rebroadcast envelope uses a Unix timestamp, not elapsed time).

## 9. OpenAPI Specification

**Source:** `src/utils/openapi.registry.mjs`

**Generator:** `@asteasolutions/zod-to-openapi` (`OpenAPIRegistry`, `OpenApiGeneratorV3`)

**Output file:** `public/openapi.json`

**Spec version:** OpenAPI 3.0.0, declared API version `0.4.1`.

### Generation Lifecycle

- **Development** (`NODE_ENV !== 'production'`): `initializeOpenApiSpec()` called during startup (`src/instrumentation.js`) generates `public/openapi.json` fresh each time.
- **Production**: startup only validates that `public/openapi.json` exists and is parseable as JSON. The file must be pre-generated and bundled into the image.

### Registered Endpoints

| Method | Path | Tags | Notes |
|--------|------|------|-------|
| GET | `/api/h1/campaign` | (none) | `season` query param documented as optional string |
| POST | `/api/h1/rebroadcast` | (none) | Body schema documents only `get_campaign_status` and `get_snapshots`; the three unimplemented actions are omitted |
| GET | `/api/h1/update` | Internal | Explicitly tagged to separate from public endpoints |

`/api/healthcheck` and `/api/og` are not registered in the OpenAPI spec.

### Viewer

The generated spec is rendered at the `/api` page route (`src/app/api/page.jsx`) using Swagger UI via a `DocsClient` component.
