## Deployment topology

Two Docker Swarm stacks run the app. Both stacks have the same shape and the same stack name, `helldiversbot`.

| | Production | Staging |
| --- | --- | --- |
| Cluster | Docker Swarm on Hetzner | Docker Swarm on three Raspberry Pi nodes |
| `app` service | 2 replicas | 2 replicas |
| `cloudflared` service | 2 replicas | 2 replicas |
| Database | One Postgres database outside the stack, shared by both `app` replicas | One Postgres database outside the stack, shared by both `app` replicas |
| `UPDATE_INTERVAL` | 20 seconds | 20 seconds |
| Image pin | `ghcr.io/elfensky/helldiversbot:vX.Y.Z` | `ghcr.io/elfensky/helldiversbot:sha-<commit>` |
| Deployed from branch | `deploy/production` | `deploy/staging` |

Each stack has a `compose.yaml` under `deploy/`. Arcane Git Sync reads that file from the CI-owned branch and applies it. The stack is read-only in the Arcane interface, and nobody runs `docker stack deploy` by hand. A rollback is a re-pin on the git side. The `image:` line on `develop` is not what runs, because CI writes the real pin on the deploy branch.

### Ingress

Each stack has its own Cloudflare Tunnel. The `cloudflared` replicas dial out to Cloudflare, so the stacks publish no ports. Both replicas register as connectors on the same tunnel. They reach the app at `http://app:3000` on the `internal` overlay network. Swarm spreads new connections over the healthy `app` replicas. The hostname routing is set in the Cloudflare Zero Trust dashboard, not in the compose files.

### One poller across replicas

Every `app` replica runs the cron thread. Each poll first claims the single `worker_heartbeat` lease row (`src/update/lease.mjs`). Postgres serializes the claim, so one replica holds the lease and polls the official API. The other replicas answer `200 {role:'standby'}`. A dead holder is replaced within the 60 s lease TTL, with no election. The poller state (`prev_events`, `last_season_observed`) lives in the same row, so a handover neither misses nor repeats a transition.

The lease, not the placement, picks the poller. For this reason:

- Any replica count is safe, and `docker service scale` needs no other change.
- No separate worker service exists.
- `WORKER_ENABLED=false` is an optional opt-out for one replica. It is not needed to scale.

### Updates and rollover

Both stacks use `order: start-first`. A new task starts and must pass the image health check before an old task stops. The old and the new build therefore serve side by side for a short time. A request for a `/_next/static` chunk of the new build can reach an old replica and get a plain-text `404`. A later request that reaches a new replica gets the `200`, and Cloudflare caches it with `cache-control: public, max-age=31536000, immutable`. This was observed on a staging rollover.

Every task also applies pending migrations before it serves (see Migrate on start in Section 1). A migration must stay backward compatible for one release, because of the side-by-side window.

### Release path

```text
v1.2.3 tag on main
  -> Build: Release
       Test & Build (verify the tagged commit)
       Build App Image (amd64) + Build App Image (arm64)  -> Publish App Manifest
       Build Migrate Image (amd64) + (arm64)              -> Publish Migrate Manifest
       Create GitHub Release (body from CHANGELOG.md)
       Pin Production -> force-pushes deploy/production
  -> Arcane Git Sync applies deploy/production
```

1. A `vX.Y.Z` tag on `main` starts Build: Release.
2. Build: Release builds the app image in two native legs, amd64 on `ubuntu-latest` and arm64 on `ubuntu-24.04-arm`. Publish App Manifest joins the legs as `:<tag>`, `:production` and `:latest`. The migrate image follows the same steps.
3. Pin Production writes the tag into `deploy/production/compose.yaml` and force-pushes it to the CI-owned branch `deploy/production`.
4. Arcane Git Sync applies that branch. No manual step is left. Production reported the new version about 10 minutes after the run started (observed for `v0.98.1`).

Rollback is a manual dispatch of Build: Release with the tag of an earlier release. A dispatch skips the builds and runs only Pin Production.

### Staging path

1. A merge to `develop` runs Check: CI. When Check: CI succeeds, Build: Staging starts.
2. Build: Staging stamps the version as `<version>-dev.<sha7>` through the `APP_VERSION` build argument. For this reason every staging build is a distinct version for the stale-tab reload and for the error tracker.
3. Build: Staging builds the app image in the same two native legs and joins them as `:staging` and `:sha-<commit>`. It builds the migrate image only when migration-related files changed.
4. Bump Staging Tag writes `sha-<commit>` into `deploy/staging/compose.yaml` and force-pushes it to `deploy/staging`.
5. Arcane Git Sync polls that branch and applies the pin. A staging roll took about 5 to 6 minutes after the pin commit (observed).

### Single-host compose

`docker-compose.yml` in the repository root is a single-host compose file for local or self-hosted use. It is not the production deployment, and it is not what either Swarm stack runs. See the `docker-compose.yml` subsection of Section 1.

## Section 1: Docker Strategy

The project uses two Dockerfiles. One image serves and migrates: the app image applies pending migrations on start. `Dockerfile.migrate` builds the manual and emergency image.

### Dockerfile.migrate

**Images:** `ghcr.io/elfensky/helldiversbot-migrate:staging` (Build: Staging) and `:<tag>`, `:production`, `:latest` (Build: Release)

**Purpose:** Manual and emergency one-shot. It runs `prisma migrate deploy` and the seed once and exits. It never stays alive. The app image runs the same two steps on start.

**Build process:**

1. Base image: `node:26-alpine`
2. Install `tini` via `apk` (init system for zombie process prevention)
3. `WORKDIR /app`
4. Copy the project `package.json` to `/tmp` as a version reference, so npm never reads it as the manifest. Copy `package-lock.json`, `prisma/`, `prisma.config.mjs`, and the two modules the seed imports (`src/validators/isValidSeason.mjs`, `src/shared/enums/events.mjs`)
5. Write a minimal `package.json` in `/app` with the project's ranges for five packages only (`prisma`, `@prisma/client`, `@prisma/adapter-pg`, `dotenv`, `zod`) and the project's `overrides`. Run `npm install` next to the project lockfile, so every version, transitive ones included, keeps the locked version and integrity hash. No full `npm ci`
6. Run `npx prisma generate` to produce the client, then remove the `/tmp` reference and the npm cache in the same layer
7. `USER node`
8. Entrypoint: `/sbin/tini --`
9. CMD: `npx prisma migrate deploy && node --experimental-strip-types prisma/seed/seed.mjs` — runs migrations first, then seeds historical season data from JSON files in `prisma/seed/seasons/`. The seed uses upserts and is idempotent (safe to re-run on every deploy). It compares each file's season against the seasons already in `h1_season` and upserts only the missing ones, so a deploy that adds one season file writes one season rather than re-running all of them (set `FORCE_SEED=true` on the migrate container to re-upsert everything — only `true`, `1` or `yes` count, so `false` correctly means off). If no season files exist, the seed exits gracefully.

The `seasons/*.json` files are produced by `prisma/seed/fetch-seasons.mjs` — a one-shot refresh script developers run on their workstations to pull the latest state from the official HD1 API. Developers then commit the updated files to git. The fetch script **never captures the currently-active season** (its `get_snapshots` response is a mid-war partial by definition), so `--to` defaults to `currentSeason - 1` and is clamped to that maximum even if specified higher. Refresh the files periodically via `node prisma/seed/fetch-seasons.mjs --force` to keep disk data in parity with the API's occasional "closing frame" writes after a season ends. See `prisma/seed/readme.md` for the full workflow.

The minimal manifest comes from the project manifest with a one-line Node script:

```dockerfile
COPY package.json /tmp/project-package.json
COPY package-lock.json ./
RUN node -e "const p = require('/tmp/project-package.json'), all = { ...p.dependencies, ...p.devDependencies }; \
      const deps = Object.fromEntries(['prisma', '@prisma/client', '@prisma/adapter-pg', 'dotenv', 'zod'].map((n) => [n, all[n]])); \
      require('fs').writeFileSync('package.json', JSON.stringify({ name: 'migrate', version: '1.0.0', private: true, type: 'module', dependencies: deps, overrides: p.overrides }))" && \
    npm install --no-audit --no-fund && \
    POSTGRES_URL=postgresql://dummy npx prisma generate
```

Prisma 7 CLI no longer auto-loads `.env` files. The `prisma.config.mjs` file imports `dotenv/config` to handle local env loading; in Docker, `POSTGRES_URL` comes from the environment. The Swarm stacks set `POSTGRES_URL_FILE` and read the value from a secret (see the `*_FILE` convention in Section 5).

This keeps the migrate image small — it carries only the Prisma CLI, not the entire application dependency tree.

### Dockerfile.app

**Images:** `ghcr.io/elfensky/helldiversbot:staging` and `:sha-<commit>` (Build: Staging); `:<tag>`, `:production` and `:latest` (Build: Release). Both are multi-arch manifests of an amd64 and an arm64 image.

**Purpose:** Runs the Next.js standalone server. Before it serves, it applies pending migrations, and the seed when its data changed (see Migrate on start).

**Build stages:**

| Stage           | Base           | What it does                                                                                                                                  |
| --------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `base`          | `node:26`      | Debian (glibc) build base, so Sharp's prebuilt glibc binary matches the runtime                                                               |
| `deps`          | `base`         | Runs `npm ci` from lockfile; fails explicitly if lockfile is absent                                                                           |
| `builder`       | `base`         | Copies `node_modules` from `deps`, copies source, runs `npx prisma generate` then `npm run build`                                             |
| `migrate-tools` | `node:26-slim` | Mirrors `Dockerfile.migrate` (Prisma CLI, schema engine, seed, generated client); copied to `/app/migrate`                                    |
| `runner`        | `node:26-slim` | Copies only `.next/standalone`, `.next/static`, `public` and `/app/migrate`; runs as a non-root numeric user                                  |

**Build inputs (builder stage):**

- Build arguments: `NEXT_PUBLIC_DEPLOY_ENV`, `APP_VERSION`, `NEXT_PUBLIC_SENTRY_DSN` and `NEXT_PUBLIC_VAPID_PUBLIC_KEY`. Next.js inlines the `NEXT_PUBLIC_*` values into the client bundle, so they must exist before `npm run build`. All four are public values.
- `APP_VERSION` replaces the `package.json` version in `next.config.mjs`. Build: Staging passes `<version>-dev.<sha7>`. Build: Release passes nothing, so the `package.json` version stays.
- Build secrets: `sentry_auth_token`, `sentry_url`, `sentry_org` and `sentry_project` are BuildKit secrets, not build arguments. A build argument lands in the provenance attestation that is published next to the image. A secret exists only for the one `RUN` that reads it. See "next.config.mjs Sentry settings" in Section 4 for what the build does with them.
- The `RUN` uses cache mounts for the npm download cache and for `.next/cache`. The cache lives in BuildKit storage and never in the image.

**Runner stage details:**

- `ARG NODE_ENV=production` — overridable at build time. Build: Staging and Build: Release both pass `NODE_ENV=production`.
- The base is `node:26-slim` (Debian, glibc). The slim image has a shell and `apt`, so its surface is larger; the app does not call a shell.
- Runs as the numeric user `65532:65532` (`USER 65532:65532`). A numeric id needs no `/etc/passwd` lookup.
- All copied files are `--chown=65532:65532`, so `.next` stays writable for the image optimizer's runtime cache. `/app/migrate` stays root-owned: the app user can read and run the tooling, not change it.
- OCI labels: `org.opencontainers.image.source`, `org.opencontainers.image.licenses`, `org.opencontainers.image.title`, `version`, `description`
- No init wrapper and no `ENTRYPOINT` of its own. The `node:26-slim` entrypoint script runs the command. The migrate image above keeps its init wrapper.
- CMD: `["node", "server.js"]` (the Next.js standalone output file)
- `EXPOSE 3000`, `ENV PORT=3000`, `ENV HOSTNAME="0.0.0.0"`, `ENV MIGRATE_ROOT=/app/migrate`, `ENV CHECKPOINT_DISABLE=1` (the Prisma CLI runs on every start and makes no update check)
- Healthcheck (Dockerfile-level): a Node `fetch` of `/api/healthcheck` every 30s, timeout 5s, start period 900s, 3 retries. Failures inside the start period do not count, and the first healthy answer ends it. Each call also refreshes the replica's `app_instance` row after the response (at most once per 20 s per process); a failed write never changes the 200/503 answer
- Server source maps in `.next/standalone` stay in the image. The app does not serve them over HTTP.

### docker-compose.yml

```text
helldiversbot
  image: ghcr.io/elfensky/helldiversbot:staging
  platform: linux/amd64
  env_file: .env.development
  ports: 127.0.0.1:50001:3000
  restart: unless-stopped
  healthcheck: Node fetch of /api/healthcheck every 60s, timeout 10s, 3 retries, 300s start_period
```

This file runs one container on one host. It uses the `:staging` image, reads its variables from a local env file, and has no replicas, no `cloudflared` and no database. The compose healthcheck replaces the image healthcheck. Neither Swarm stack uses it; see Deployment topology.

The port binding `127.0.0.1:50001:3000` deliberately limits exposure to the host loopback interface. External traffic must arrive through a reverse proxy (e.g., nginx or Caddy) on the host.

`docker-compose.ci.yml` is a separate file for the Check: Docker Smoke workflow. It builds the app image from the working tree and starts it with a Postgres container.

### Migrate on start

Every app process runs `migrateOrWait()` (`src/update/migrateOnStart.mjs`) from `instrumentation.js`, before the worker starts and before Next serves a request.

- A dedicated `pg` session takes `pg_advisory_lock(599000001)`. Replicas take turns, so Prisma's own fixed 10 s migrate lock never contends.
- The session runs `prisma migrate deploy`, then the seed. The session ends afterwards, which releases the lock on success and on failure.
- Each of the two child processes has a 5 min limit, inside the image's 15 min health-check start period. A stuck child is killed, so the attempt fails, reports and releases the lock. A lost lock session also kills the running child, because another replica can then take the lock.
- The seed runs only when the sha256 of `prisma/seed/seed.mjs` plus `prisma/seed/seasons/*.json` differs from the hash in the `seed_state` table. A failed seed stores nothing, so the next attempt seeds again.
- `migrateOrWait()` never throws. A failure logs `[migrate] failed: …`, reports to GlitchTip with stage `migrate-on-start`, and retries after 30 s, 60 s, 2 min, then every 5 min.
- Next holds requests until `register()` resolves. A migrating task stays Starting, and Swarm's start-first update keeps the old tasks serving.
- `MIGRATE_ROOT` names the folder with the Prisma CLI and the `prisma/` tree. The image sets `/app/migrate`; the default is the process cwd.
- Every migration stays backward compatible for one release (expand/contract), because start-first runs the old and the new version side by side. Rollback is a forward migration: Prisma has no down migrations.

### Staging (`staging.docker.yml`)

**Trigger:** Successful completion of the `CI` workflow on `develop` (`workflow_run`), or manual `workflow_dispatch`.

This pipeline used to trigger on the push itself, which meant it raced CI — the image built, published and deployed while lint, typecheck and tests were still running, so a red CI was a note attached to an already-shipped build. `develop` accepts direct merges without a PR, so the required-status-check that guards `main` never applies here; this gate is the only one.

Two consequences worth knowing. `workflow_run` resolves the workflow file from the **default branch** (`develop`), so edits to it only take effect once merged there. And every `checkout` pins `github.event.workflow_run.head_sha` — the commit CI actually tested — because a `workflow_run` checkout otherwise defaults to the branch tip, which may have moved on.

**Jobs:** A `detect-migration` job detects which files were modified. `build-app` always runs. `build-migrate` only runs when migration-related files changed (or on manual `workflow_dispatch`). A `cleanup` job runs after both builds complete (or are skipped).

| Job                | Dockerfile           | Tag pushed                                       | Condition                                                                                                        |
| ------------------ | -------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `detect-migration` | ---                  | ---                                              | Always runs; outputs `migrate` boolean from `git diff HEAD^ HEAD`                                                |
| `build-migrate`    | `Dockerfile.migrate` | `ghcr.io/elfensky/helldiversbot-migrate:staging` | Only when `prisma/**`, `prisma.config.mjs`, `package.json`, `package-lock.json`, or `Dockerfile.migrate` changed |
| `build-app`        | `Dockerfile.app`     | `ghcr.io/elfensky/helldiversbot:staging`         | Always                                                                                                           |

Both build jobs pass `NODE_ENV=production` as a build arg.

**Registry auth:** `secrets.GITHUB_TOKEN` — the default token with `contents: write` and `packages: write` permissions declared at the workflow level.

**Cleanup job:** Uses `snok/container-retention-policy@v3.0.1`. Deletes untagged versions of both `helldiversbot` and `helldiversbot-migrate` packages that are older than 30 minutes. This keeps GHCR from accumulating dangling layers from every push. Authenticated via `secrets.GHCR_CLEANUP_TOKEN` — a **classic** PAT with the `delete:packages` scope (the action rejects fine-grained tokens, and the default `GITHUB_TOKEN` can't delete user-account packages).

### Production (`release.docker.yml`)

**Trigger:** Version tags matching the pattern `v*.*.*` (e.g. `v1.2.3`)

**Jobs:** A `verify` job runs lint, typecheck, unit tests and build against the tagged commit; `build-app` and `build-migrate` both `needs: verify`, and `github-release` needs both.

`main`'s branch protection already requires the `Test & Build` check to merge, so release code has normally passed. *Normally* is the gap: a tag can be pushed at any commit — an older one, a hotfix merged with an admin override, a hand-moved tag — and `ci.yml` does not run on tags at all. The `verify` job makes the tag itself the unit that gets checked.

It duplicates `ci.yml`'s steps rather than sharing them through a `workflow_call` reusable workflow. That would rename the check from `Test & Build` to `<caller> / Test & Build`, and `main`'s required status check matches that exact string — every PR to `main` would block forever waiting for a check that no longer reports.

**Tags pushed:**

```
ghcr.io/elfensky/helldiversbot:{git-tag}
ghcr.io/elfensky/helldiversbot:production
ghcr.io/elfensky/helldiversbot:latest
```

**Version extraction:** The workflow reads the version from `package.json` via `jq -r '.version' package.json` and injects it into the image via the `VERSION` ARG (used by the Dockerfile label `version="${VERSION}"`).

**Registry auth:** `secrets.GITHUB_TOKEN` — the workflow's `permissions: contents: write` + `packages: write` grant it enough access to push images to GHCR and create the GitHub Release, so no personal access token is needed.

**GitHub Release:** Created by `softprops/action-gh-release@v2`. The release body is sourced from `RELEASE.md` at the repository root.

### Metrics (`metrics.yml`)

**Trigger:** Scheduled (Mondays at 00:00 UTC, Fridays at 06:00 UTC), or manual dispatch.

**Job:** Generates a PageSpeed Insights badge SVG using `lowlighter/metrics@latest` targeting `https://helldivers.bot`. The resulting `metrics.plugin.pagespeed.svg` is committed back to the repository. Requires `secrets.PAGESPEED_TOKEN`.

### Full flow

```
register()   [src/instrumentation.js]
│
├── NEXT_RUNTIME === 'nodejs'
│   └── import sentry.server.config.js     → Sentry.init() for server runtime
│
└── NEXT_RUNTIME === 'nodejs'
    └── initializeHelldivers1Api()
        │
        ├── Step 1: initializeEnvironmentVariables()   [src/shared/utils/initializeEnv.mjs]
        │   ├── checkDatabase()    → POSTGRES_URL                              ← REQUIRED, throws
        │   ├── checkUpdates()     → UPDATE_KEY, UPDATE_INTERVAL               ← REQUIRED, throws (PORT optional)
        │   ├── checkAnalytics()   → UMAMI_SITE_ID, SENTRY_DSN, SENTRY_AUTH_TOKEN  ← OPTIONAL, warns
        │   ├── checkAuth()        → BETTER_AUTH_SECRET + 5 auth vars          ← OPTIONAL, warns (partial = throws)
        │   └── Returns { auth: boolean, analytics: boolean }
        │
        ├── Step 2: initializeOpenApiSpec()            [src/utils/initialize.openapi.mjs]
        │   ├── development: generates public/openapi.json from the OpenAPI registry, validates JSON
        │   ├── production:  reads existing public/openapi.json, validates it parses as JSON
        │   └── false → throw (crashes the process)
        │
        └── Step 3: initializeWorker()                 [src/shared/utils/initializeWorker.mjs]
            ├── Resolves worker path:
            │   ├── development: path.resolve(process.cwd(), 'public/workers/cron.js')
            │   └── production:  path.resolve('/app/public/workers/cron.js')
            ├── new Worker(workerPath)
            ├── worker.postMessage({ key, interval, port })
            ├── Attaches message/error/exit handlers
            ├── Registers SIGINT/SIGTERM handlers that terminate the worker before exit
            └── false → throw (crashes the process)
```

### Failure behavior

Every initialization step fails hard: any error or falsy return causes a `throw new Error(...)` inside the `register()` function. Since Next.js does not catch errors thrown from `register()`, this crashes the process. There is no graceful degradation. The intent is that Docker's `restart: unless-stopped` will restart the container, giving the underlying problem (missing env var, bad database, missing OpenAPI spec) a chance to be resolved.

### onRequestError export

`src/instrumentation.js` also exports:

```js
export const onRequestError =
    process.env.SENTRY_DSN ? Sentry.captureRequestError : () => {};
```

Next.js calls this hook for errors that occur inside Server Components, middleware, and proxied routes — errors that do not surface through the normal React error boundary. This is the server-side equivalent of `global-error.jsx`. The DSN-presence gate means localhost reports too when `SENTRY_DSN` is set in `.env.development`; environments stay distinguishable via the `environment` tag.

## Section 4: Error Tracking (Sentry / GlitchTip)

The project uses the Sentry SDK (`@sentry/nextjs`) but targets a **self-hosted GlitchTip** instance rather than Sentry SaaS. GlitchTip is Sentry-protocol-compatible and supports error aggregation and performance traces but not session replay.

### Configuration files

| File                             | Runtime | Role                                                                         |
| -------------------------------- | ------- | ---------------------------------------------------------------------------- |
| `sentry.server.config.js`        | Node.js | `Sentry.init()` called on server startup via `instrumentation.js`            |
| `src/instrumentation-client.js`  | Browser | `Sentry.init()` called when a page loads in the browser                      |
| `src/app/api/glitchtip/route.js` | Node.js | Client tunnel — proxies Sentry envelopes to GlitchTip, bypassing ad blockers |

### Shared SDK settings

```js
{
    dsn: process.env.SENTRY_DSN,        // server: SENTRY_DSN, client: NEXT_PUBLIC_SENTRY_DSN
    environment:                        // "development" | "staging" | "production"
        process.env.NEXT_PUBLIC_DEPLOY_ENV ||
        process.env.DEPLOY_ENV ||
        process.env.NODE_ENV,
    dataCollection: {                   // server value; keeps the v10 scope
        httpBodies: ['incomingRequest'],
        databaseQueryData: false,
        stackFrameVariables: false,
    },
    tracesSampleRate: 1.0,              // 100% of requests traced
    debug: false,
}
```

Client-only additions: `autoSessionTracking: false` (GlitchTip doesn't support sessions), `tunnel: '/api/glitchtip'` (ad blocker bypass), `dataCollection: { httpBodies: [] }` (the browser sends no HTTP bodies).

Server init lives in `sentry.server.config.js` and is loaded from `src/instrumentation.js` only when `SENTRY_DSN` is set — no production gate, so localhost reports too. Client init lives in `src/instrumentation-client.js` and runs on every page load whenever `NEXT_PUBLIC_SENTRY_DSN` is set.

### Client tunnel

The `/api/glitchtip` route proxies Sentry envelope payloads to GlitchTip's ingest endpoint. This prevents ad blockers from blocking error reports since the SDK sends to the app's own domain. The tunnel extracts the DSN's public key and forwards to `https://<host>/api/<project>/envelope/?sentry_key=<key>&sentry_version=7`.

### Error boundaries

Three levels of error isolation:

1. **`global-error.jsx`** — last-resort boundary wrapping the entire React tree. Renders its own `<html>`/`<body>` since the root layout is unavailable. Reuses the shared `RouteError` component.
2. **Route-level `error.jsx`** — at root (`src/app/error.jsx`) and archives (`src/app/archives/error.jsx`). Thin wrappers around `RouteError` that catch errors within the layout.
3. **`ComponentErrorBoundary`** — React class component wrapping Galaxy Map, Regions, Stats, Dashboard, and Timeline. Shows inline "failed to load" + retry button. Layout containers stay outside boundaries to preserve CSS grid/flex structure on error.

Each boundary calls the shared `reportError(error, { boundary })` helper (`src/shared/utils/observability.mjs`) so the user-visible failure reaches GlitchTip with the boundary name as context. `ComponentErrorBoundary` also passes the React `componentStack` for attribution. The same helper is used at every API-route 5xx path; calling it with a falsy error is a no-op so wiring it next to existing `errorResponse(5xx, ...)` sites is safe.

The Sentry browser SDK's global `window.onerror` / `unhandledrejection` handlers continue to catch uncaught client errors automatically — `reportError` exists for everything that gets `try/catch`'d or routed through an error boundary, which the global handler can't see.

### Reporting paths

`src/shared/utils/observability.mjs` exposes one function:

```js
export function reportError(error, context = {}) {
    if (!error) return;
    const { level, ...extra } = context;
    Sentry.captureException(error, { level, extra });
}
```

Call sites pass a `route` and `stage` tag for API routes (e.g. `{ route: '/api/h1/update', stage: 'season' }`) or a `boundary` tag for React error boundaries. The `level` field maps to Sentry severity — used at `update/route.js` to mark the closing-pass season-fetch as a warning instead of an error since the code path is explicitly non-fatal.

The tunnel route (`/api/glitchtip`) is deliberately not wired with `reportError`; capturing there would self-loop when GlitchTip itself is the failing upstream.

Caught errors flowing through `src/shared/utils/tryCatch.mjs` — the project's canonical error-handling pattern, used at ~30+ call sites — are also auto-reported with `source: 'tryCatch'` and `level: 'warning'`. The explicit `reportError(...)` calls at 5xx sites still fire at the default `error` level. Sentry groups by stack-trace fingerprint so duplicate events for the same throw roll up into one issue, while the severity tag keeps caught-and-recovered errors visually distinct from user-visible failures in the inbox.

### Service worker error bridge

The service worker at `src/sw.js` runs in a separate worker context with no DOM, so it can't import the Sentry browser SDK directly. The `push` and `notificationclick` handlers are wrapped with try/catch (synchronous) and `.catch()` (on the async chains inside `event.waitUntil`); failures `postMessage` a structured `{ type: 'sw-error', error: { message, name, stack }, context }` envelope to all controlled clients via `self.clients.matchAll()`. The receiving end lives in `src/shared/utils/swErrorBridge.mjs` — registered from `instrumentation-client.js`, it reconstructs the Error and calls `reportError(err, { source: 'sw', ...context })`. When no clients are open (push received with all tabs closed) the SW falls back to `console.error`, visible from `chrome://serviceworker-internals` during triage. Errors are re-thrown after the postMessage so the SW event loop still sees the rejection — original behavior preserved.

### Worker uptime heartbeat

`public/workers/cronLogic.js` POSTs to `GLITCHTIP_HEARTBEAT_URL` after each successful (`response.ok`) poll of `/api/h1/update`. Fire-and-forget — heartbeat fetch failures are swallowed and don't affect the poll loop. GlitchTip's uptime monitor flips red when heartbeats stop, which surfaces: worker thread death, sustained 5xx from the API route, or DB unavailability. The worker reads the URL from `process.env` (Node `worker_threads` inherits the parent's env by default), so no message passing is needed.

### Analytics proxy

Umami v3 analytics use a same-origin proxy to bypass ad blockers:

1. **Script proxy:** `/stats.js` and `/recorder.js` are route handlers (`src/app/stats.js/route.js`, `src/app/recorder.js/route.js`, shared code `proxyUmamiScript` in `src/shared/utils/umami.mjs`). Each fetches `script.js` or `recorder.js` from `UMAMI_SITE_URL` with no visitor headers, so visitor cookies, the auth session cookie included, never reach the Umami host. A Next.js rewrite would forward them.
2. **Data proxy:** `/api/send` → `/api/umami` (Next.js rewrite) → `umami.lav.ren/api/send` (API route proxy)
3. **Recorder data:** `/api/record` and `/api/websites/:id/recorder` are Next.js rewrites to `umami.lav.ren`, set in `next.config.mjs` and not read from `UMAMI_SITE_URL`: rewrites are resolved at build time, and that variable exists only at runtime. The recorder calls them with `credentials: "omit"`, so the browser attaches no cookie. `RecorderScript` renders the recorder only for browsers without the `umami.disabled` opt-out flag. Replays and heatmaps stay inert until they are turned on for the site in Umami.

The proxy writes the visitor's IP from Cloudflare's `cf-connecting-ip` into the hit as `payload.ip`, so Umami uses the visitor, not this server, for its cookieless session hash and its location. Without it, the relay's second pass through Cloudflare labels every hit with the server's IP and country. The app sets no Content-Security-Policy header and the production edge sets one. Every Umami request (script, send, recorder) is same-origin, so `'self'` in `script-src` and `connect-src` covers it and no Umami domain needs an allowance.

Env vars: `UMAMI_SITE_URL` (domain without protocol, e.g., `umami.lav.ren`), `UMAMI_SITE_ID` (website UUID).

### next.config.mjs Sentry settings

The `withSentryConfig` wrapper (imported from `@sentry/nextjs/config`) controls build-time behavior. It runs only when `SENTRY_AUTH_TOKEN` is set:

```js
export default process.env.SENTRY_AUTH_TOKEN ?
    withSentryConfig(finalConfig, {
        authToken: process.env.SENTRY_AUTH_TOKEN,
        org: process.env.SENTRY_ORG,
        project: process.env.SENTRY_PROJECT,
        sentryUrl: process.env.SENTRY_URL,
        sourcemaps: { deleteSourcemapsAfterUpload: true },
    })
:   finalConfig;
```

- **Builds with the token** (Build: Staging, Build: Release) generate the browser source maps and upload them to GlitchTip as debug-ID bundles. Then they delete the maps and their `sourceMappingURL` comments from `.next/static`. The image ships no browser maps.
- **Builds without the token** skip the wrapper. They emit no browser maps.
- **Server maps** in `.next/standalone` stay in the image. The app does not serve them over HTTP.
- **No `silent` option.** It hid two upload failures in 2026-07 and 2026-08 (#496). Upload errors must print in the build log.

The `authToken`, `org`, `project`, and `sentryUrl` env vars are only used during builds.

## Section 5: Environment Variables

Variables are checked at startup by `initializeEnvironmentVariables()` in `src/shared/utils/initializeEnv.mjs`. The function uses **progressive enhancement**: core variables throw on missing (app cannot function), while auth and analytics variables warn and degrade gracefully. Returns `{ auth: boolean, analytics: boolean }` so the startup log shows which features are active.

**Validation rules:**

- **Core (database, worker):** Missing → throws, crashes the process.
- **Auth:** `BETTER_AUTH_SECRET` absent → all auth disabled (warn). `BETTER_AUTH_SECRET` present but other auth vars missing → throws (partial config is a misconfiguration).
- **Analytics:** Missing → warns. `SENTRY_DSN` set without `SENTRY_AUTH_TOKEN` → warns about degraded source maps.

### Connection string formats

Local development connects directly to the host machine:

```
postgresql://user:pass@127.0.0.1:5432/dbname
```

Inside Docker, the app container reaches the host's PostgreSQL via the special Docker DNS name:

```
postgresql://user:pass@host.docker.internal:5432/dbname
```

The `.docker.env` file (not checked into version control) holds the Docker-specific values and is referenced by both services in `docker-compose.yml`.

## Section 6: PWA Assets

The app is an installable Progressive Web App. PWA assets are static files that ship with the build — no build-time generation step is needed.

### Web App Manifest

Source: `src/app/site.webmanifest` (auto-served by Next.js from the app directory)

Linked in `<head>` via `metadata.manifest` in `src/app/layout.jsx`. Contains `start_url`, `scope`, `orientation: portrait`, and two icons with `purpose: "any maskable"`.

### iOS Splash Screens

20 portrait PNG images in `public/splash/` covering all current iPhone and iPad device sizes. Generated once via `npx pwa-asset-generator` with solid `#282828` background + centered logo. Linked via `<link rel="apple-touch-startup-image">` tags with device-specific media queries in `layout.jsx`.

To regenerate after logo changes:

```bash
npx pwa-asset-generator public/images/logo_square.png public/splash \
  --splash-only --background "#282828" --padding "30%" --type png
# Then delete landscape images (width > height) since orientation is portrait-only
```

### Cache Headers (next.config.mjs)

Static assets served from `public/` have cache headers configured in `next.config.mjs`:

| Asset Type | `max-age` | `immutable` |
| ---------- | --------- | ----------- |
| Favicons   | 1 day     | Yes         |
| Fonts      | 1 year    | Yes         |
| Icons      | 7 days    | Yes         |
| Images     | 7 days    | Yes         |
| SVGs       | 7 days    | Yes         |
| Workers    | 1 day     | Yes         |

The service worker (`public/sw.js`) has a 1-day `max-age`, ensuring browsers check for new versions daily. The SW itself handles cache versioning via the `CACHE_NAME` constant.
